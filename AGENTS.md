# AGENTS.md

Guidance for AI coding agents working in this repository.

## What this is

Bookkeeper is a self-hosted household finance tracker for two people
(replacing an Excel workbook). It tracks utility bills with rolling-average
trends, recurring/annual bills, personal subscriptions, category-level
monthly spend, income by pay cadence, and a "standard month" income vs.
expense projection. It's built to run as a single Docker container on a
home server (unRAID) with no cloud dependency — one SQLite file holds all
data. See [README.md](README.md) for product-level detail, backup
procedures, and the list of permanent non-goals / deferred work.

## Courtesy
The end user checks all changes after being made and before committing,
always ask before committing and pushing.
The local dev server should always be left running after work is completed
and if it is required to be turned off for a change, it should be returned
to running again at the end of the session.
Clean up after yourself, do not leave any other sessions active.

## Monorepo layout

pnpm workspace with two apps, no shared packages:

```
apps/api/   AdonisJS 7 + Lucid ORM + SQLite — the backend and single deploy artifact
apps/web/   SvelteKit (Svelte 5) + Tailwind CSS — built as a static SPA
prompts/    Original planning prompts used to scaffold the project (historical, not living docs)
```

In production, `apps/web` is built to static files and copied into
`apps/api/public`; AdonisJS serves both the API and the SPA as one process
(see the root `build` script and `Dockerfile`). There is no reverse proxy
or SSR — the SPA fallback route in `apps/api/start/routes.ts` serves
`index.html` for any non-API, non-asset path.

## Commands

Run from the repo root unless noted:

```bash
pnpm install
pnpm dev:api             # AdonisJS on :3333
pnpm dev:web             # SvelteKit dev server on :5173, proxies /api to :3333
pnpm lint                # eslint on both apps
pnpm lint:fix
pnpm typecheck           # tsc --noEmit (api) + svelte-check (web)
pnpm format              # prettier --write .
pnpm test                # full suite: api (Japa) then web (Vitest)
pnpm build               # web build -> apps/api/public -> api build
```

Per-app extras:

```bash
pnpm --filter api exec node ace migration:run
pnpm --filter api exec node ace db:seed        # creates logins from the workbook's "Users" sheet
pnpm --filter api test:coverage                # text + HTML report in apps/api/coverage/
pnpm --filter web test:coverage                # text + HTML report in apps/web/coverage/
```

Before first run, copy `apps/api/.env.example` to `apps/api/.env` and fill
in `APP_KEY` (`node ace generate:key`) and `SEED_WORKBOOK_PATH` (path to
the `Joint Account Workbook.xlsx`, whose "Users" sheet - `Name`, `Email`,
`Password` columns - `db:seed` reads to create logins).

## API (`apps/api`) — AdonisJS conventions

- **Layering**: routes (`start/routes.ts`) → controller → validator
  (VineJS, `app/validators/`) → Lucid model → transformer
  (`app/transformers/`, hand-written serialization, not raw model JSON) →
  controller returns `{ data: ... }`. Follow this shape for new endpoints;
  see `app/controllers/categories_controller.ts` as a representative
  example.
- **Subpath imports**: the codebase uses Node subpath imports, not relative
  paths — `#controllers/*`, `#models/*`, `#services/*`, `#validators/*`,
  `#transformers/*`, `#middleware/*`, `#database/*`, `#tests/*`, etc. (full
  map in `apps/api/package.json` under `"imports"`). Use these instead of
  `../../` paths.
- **`database/schema.ts` and `database/schema_rules.ts` are generated** —
  regenerated by running migrations, never hand-edit them.
- **Soft deletes**: `destroy` actions generally set `isActive = false`
  rather than removing rows (see `CategoriesController.destroy`) —
  check existing controllers for a model before assuming a hard delete.
- **Services** (`app/services/`) hold non-trivial business logic pulled out
  of controllers — rolling averages, standard-month projection, income
  cadence math, utility billing-period logic, and the one-time xlsx import
  parsers (`app/services/import/`). Put new date/frequency/aggregation
  logic here, not in controllers.
- **Auth**: session/cookie-based, exactly two user accounts (household
  members), seeded via `db:seed` from the workbook's "Users" sheet (not
  `.env` — see `database/seeders/user_seeder.ts` and
  `app/services/import/parse_users_sheet.ts`). No self-registration, no
  roles/permissions system — don't build toward multi-tenancy. If you need
  to actually log in to the running app (e.g. to verify a UI change in a
  browser), the login credentials (`Name`, `Email`, `Password` columns) are
  in the same `Joint Account Workbook.xlsx` referenced by
  `SEED_WORKBOOK_PATH`, under its "Users" sheet — never hardcode or commit
  the actual email/password anywhere in this repo.
- **HotHook** boundaries are configured for controllers and middleware
  (`hotHook` in `package.json`) — the dev server HMRs those without a full
  restart.

## Web (`apps/web`) — SvelteKit conventions

- **Svelte 5 runes** throughout (`$state`, not Svelte 4 stores) — see
  `src/lib/stores/auth.svelte.ts` and `theme.svelte.ts` for the pattern:
  a plain class holding `$state` fields, instantiated once as a module
  export, with exported functions to mutate it.
- **API layer** (`src/lib/api/*.ts`): one thin wrapper module per resource
  (`categories.ts`, `income.ts`, etc.), each just calling the shared
  `api.get/post/patch/put/delete` helpers from `src/lib/api.ts`. Add new
  endpoints by following the existing per-resource file pattern, not by
  calling `fetch` directly from components.
- **`src/lib/api.ts`** is the one place that knows about `/api` prefix,
  credentials, the `XSRF-TOKEN` cookie/header dance, and unwrapping
  `{ data }` responses — don't duplicate that logic elsewhere.
- **Static adapter**: `@sveltejs/adapter-static` — this is a pure SPA, no
  server-side load functions that depend on request context beyond what
  runs in the browser after mount.
- Tailwind CSS v4 via `@tailwindcss/vite` (no separate `tailwind.config.js`
  — config lives in CSS via the Vite plugin).

## Testing

- **API**: Japa. Unit tests (`tests/unit/`) cover import parsers, services,
  and every validator. Functional tests (`tests/functional/`) hit every
  controller over HTTP using `@japa/api-client`, wrapped in a per-test DB
  transaction (`tests/bootstrap.ts`) against an isolated
  `apps/api/tmp/test.sqlite3` — never the dev database. The API targets
  100% statement/branch/function/line coverage; the two accepted
  exceptions (the one-time `import:xlsx` command, and a handful of
  `c8 ignore`-annotated unreachable branches) are documented in
  [README.md](README.md#running-tests) — match that bar for new code
  rather than lowering it, and comment any new `c8 ignore` the same way.
- **Web**: Vitest + `@testing-library/svelte`, jsdom environment, timezone
  pinned to `UTC` (`vitest.config.ts`) so date-formatting assertions are
  deterministic. Every `$lib` module and every route/component has a
  colocated `*.spec.ts`. Tests mock `$app/navigation` / `$app/state` and the
  relevant `$lib/api/*` module (see `src/lib/api/categories.spec.ts`) rather
  than hitting a real server — don't spin up the API in web tests. Coverage
  is high-90s statement/function/line; branch coverage (~80%) is
  deliberately not chased to 100% (see README) — mostly decorative template
  conditionals, not business logic.
- Run `pnpm test` (both apps) before considering a change done; run the
  single-app `test:coverage` script if you need to check the number didn't
  regress.

## Formatting & linting

- Prettier: no semicolons, single quotes, 100-char print width,
  `prettier-plugin-svelte` + `prettier-plugin-tailwindcss` (root
  `.prettierrc.json`). Run `pnpm format` rather than hand-formatting.
- ESLint: `@adonisjs/eslint-config` for the API; `typescript-eslint` +
  `eslint-plugin-svelte` + `eslint-config-prettier` for web. Both apps lint
  independently (`pnpm lint`).
- TypeScript strict mode everywhere (`tsconfig.base.json`):
  `noUncheckedIndexedAccess` is on, so array/index access is typed
  `T | undefined` — handle that rather than adding a non-null assertion
  reflexively.

## Known sharp edges (see README for full list)

- **Number-input null-vs-NaN gap**: several web forms guard a required
  amount field with `Number.isNaN(amount)`, but clearing an already-filled
  Svelte number input yields `null`, not `NaN`, so the guard silently lets
  a blank field through as `amount: null`. If you touch one of these forms,
  the fix is `Number.isNaN(x) || x === null` at the call site — apply it
  there rather than treating it as pre-existing and out of scope.
- **Single currency, hardcoded AUD formatting, no multi-tenant/reverse-proxy
  support** — these are deliberate non-goals, not gaps to fill in.
